RAG 是先将知识作为向量存储到向量数据库
再将用户输入的提示词 去和 向量数据库中的 知识向量进行**相似度匹配**，检索出相关的片段
最后将检索出来的内容 + 用户提示词一起发送给大模型，生成最终回答
==RAG是模型获取知识的能力，根据用户提问选择性获取知识。==

### 1 为什么会有RAG？
**大模型本身有 3 个问题：**
- 知识过时（只学到训练截止日期之前的内容）
- 存在幻觉（会胡编乱造）
- 不知道内部私有数据（你的文档、业务规则等）

RAG就是用来解决这三个问题，1.检索外部知识库融入最新知识 2.基于真实检索，减少模型幻觉 3.获得私有数据

### 2 召回率
在 RAG 检索系统中，召回率指的是在所有真正相关的文档中，有多少被成功地检索了出来。
**计算方式：召回率 = 检索到的相关内容数量 ÷ 所有相关内容的总数量**

假设知识库中有 6 条与这个问题高度相关的内容，但系统只返回了其中 3 条。那么，召回率就是 3 ÷ 6 = 50%。
在 RAG 系统中，召回率尤为关键，因为大模型能不能“答对”，很大程度取决于有没有拿到相关内容；召回率越高，大模型 在生成答案时能参考的有效信息就越多，回答的质量和准确性也就越有保障。

### 3 RAG分块策略
#### 3.1 文档为什么要分块
1. ==向量模型== embedding-model 对输入文本长度有严格限制，文档太长则无法向量化
2. 提高语义匹配的相关性和精度，因为RAG的本质是通过语义的相似度来检索相关的内容，分块意味着==更精准的语义单元==、意味着更高的检索质量
3. ==大模型的会话==中也是有上下文窗口限制的，另外过大的内容也导致token占用更多

#### 3.2 固定大小分块
这是最简单直接的分块方法。根据LangChain源码，这种方法的工作原理分为两个主要阶段：

（1）**按段落分割**：`CharacterTextSplitter` 采用默认分隔符 `"\n\n"`，使用正则表达式将文本按段落进行分割，通过 `_split_text_with_regex` 函数处理。
（2）**智能合并**：调用继承自父类的 `_merge_splits` 方法，将分割后的段落依次合并。该方法会监控累积长度，当超过 `chunk_size` 时形成新块，并通过重叠机制（`chunk_overlap`）保持上下文连续性，同时在必要时发出超长块的警告。

需要注意，`CharacterTextSplitter` 实际实现的并非严格的固定大小分块。根据 `_merge_splits` 源码逻辑，这种方法会：
- **优先保持段落完整性**：只有当添加新段落会导致总长度超过 `chunk_size` 时，才会结束当前块
- **处理超长段落**：如果单个段落超过 `chunk_size`，系统会发出警告但仍将其作为完整块保留
- **应用重叠机制**：通过 `chunk_overlap` 参数在块之间保持内容重叠，确保上下文连续性

#### 3.3 递归字符分块
递归分块遇到超长段落会以更细粒度进一步分块
**与固定大小分块的关键差异**：
- 固定大小分块遇到超长段落时只能发出警告并保留。
- 递归分块会继续使用更细粒度的分隔符（句子→单词→字符）直到满足大小要求。

#### 3.4 语义分块
按照文本的语义进行分块
1. 将文档按段落或句子初步分段
2. 对每个分段进行向量化 (embedding)
3. 从第一个分段开始
	`a` 若与下一个分段 余弦相似度高 -> 则合并两个分段为一个分段，继续与下一段进行比较
	`b` 直到相似度显著下降 -> 则不再继续合并，之前合并的内容就形成了一个完整的"块"
4. 重复上述过程

### 4 Query Rewriting策略
多轮对话中用户的提问普遍存在**指代性、省略性、上下文依赖性**的特点，RAG 原生的检索模块（如向量数据库、关键词检索）不具备“理解语境”的能力，只能基于输入的 Query 字面语义去匹配文档，直接检索孤立的后续问题必然导致召回偏差，甚至完全失效。

Query Rewriting策略，利用轻量LLM对多轮对话进行上下文改写

### 5 不同Embedding模型的对比与分析
+ 按输入类型分类（文字，语音，图片）
+ 按建模目标分类（通用，垂直领域）

优先级：输入类型->成本/性能->验证效果

Eembedding向量将非结构数据映射为固定维度的稠密数据向量，让向量空间的距离对应真实世界的特征相似度。我们向量化都是采用现有embedding嵌入模型。

**为什么使用text-embedding-v3?**
+ 文本嵌入模型（我们的文档中只有极少数图片，文本模型价格便宜）
+ 中文语料训练
+ text-embedding维度灵活64-1024

### 6 RAG和工具调用的关系
RAG本身其实可以理解为通过工具调用实现的一种能力。在我的项目里，我把RAG检索封装成Tool，由模型在ReAct过程中动态决定是否调用。

### 7 RAG的缺陷
+ 数据质量
+ 分块策略的两难困境（块太小语义聚焦但是失去了上下文，块太大保留了上下文但引入噪声影响匹配精度）
+ 多跳问题 
+ 评估困难与效果不可预期（在一个测试集表现良好的系统，面对用户千奇百怪的提问效果可能会大幅退化）

**即使用了RAG，也会出现幻觉**
+ 召回率低
+ 文档本身没有包含这部分数据或者文档本身数据就有问题
+ 上下文太长了
+ 检索内容忽视，过于依赖参数化知识
+ 生成偏移，生成模型在语言组织与内容整合过程中，仍可能引入检索结果之外的信息
+ 模型倾向输出高流畅度、高置信度的文本
