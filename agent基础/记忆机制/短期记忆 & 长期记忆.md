短期记忆
- 存储目的：维持上下文连续性  
- 数据形态：原始对话信息  
- 调用方式：全量拼入 prompt  
- 生命周期：会话级

长期记忆
+ 存储目的：实现跨会话的个性化/知识持久化
+ 数据形态：结构化或者向量化的核心信息
+ 调用方式：按需检索关键词
+ 生命周期：用户级

## 为什么不能用短期记忆的方式处理长期记忆？
+ **Prompt 长度爆炸**：用户一年的核心信息可能有上百条，全拼进去会远超模型的上下文窗口（比如4k tokens），模型直接报错；
+ **模型注意力分散**：无关信息（比如用户半年前的饮食偏好）会**干扰**模型对当前问题的理解，比如用户问RAG的Java落地，模型却关注“用户不吃辣”的信息，回答偏离重点。

同理，短期记忆需要强上下文关系，必须全量保留，检索会导致关键上下文丢失，比如用户在上一个问题下追问，模型可能会不知所云。

## 长期记忆与短期记忆的实现
### 1 短期记忆的实现
1. **数据结构**：使用一个双向队列或列表来保存对话消息 `List<Message>`。
2. **消息格式**：每条消息通常包含`role`（`user`, `assistant`, `system`）和`content`。
3. **管理策略**：==**滑动窗口+总结摘要**==。只保留最近的 N 轮对话 或 N 个Token。当窗口满了的时候，用一个单独的 LLM 调用对更早之前的对话/信息生成一个简短的摘要，只保留最近的 N 轮对话 或 N 个Token。这能在有限上下文内保留更多“精髓”。
### **2 长期记忆的实现**
通常包含两个核心组件：**记忆写入器** 和 **记忆读取器**。
#### **2.1 长期记忆的存储与写入**
- **触发时机**：何时创建一条长期记忆？（==从模型自动提取改成了主动录入==）
	- **显式指令**：用户说“请记住我喜欢蓝色”。
	- **隐式提取**：模型在对话中自动识别出关键事实（如用户的工作、项目名），并决定存入记忆。（困难点： ==在对话中何时创建一条长期记忆==（需要 特别地依赖LLM识别出用户的含义  或者 识别到关键词才去创建一条长期记忆，这种方法同样也不够精准））
- **存储格式**：
	- **结构化**：存入关系型数据库。表结构如 `(user_id, key, value, timestamp)`。例如 `(”user123″, “favorite_color”, “blue”, “2023-10-27”)`。适合存储明确的键值对信息。
	- **向量化**：将 **对话片段或提取的事实** 转换成**向量嵌入**，存入向量数据库（如Milvus, Pinecone）。这使得我们可以进行**语义搜索**。当用户问“我之前跟你提过什么关于颜色的事？”，即使他没说“蓝色”，系统也能通过**向量相似度(即语义)** 找到相关记忆。

#### **2.2 长期记忆的读取与召回**
- **触发时机 (怎么知道要去读取信息？)**：有两种可选的触发方式
	- ① 默认触发（每次构造 Prompt 前都查）；
	- ② 精准触发（检测到 “记得 / 之前 / 偏好” 等关键词时查）
- **召回策略**：
	- **按记忆类型分 (怎么知道要去哪里读取信息)**：
		- ①结构化记忆→MySQL（user_id 分表）；
		- ②向量化记忆→向量库（Milvus/ES，user_id 过滤）
	- **怎么知道要读取什么信息？**
		- ①结构化记忆：提取用户问题关键词，匹配数据库的`key`字段；
		- ②向量化记忆：将问题转为向量，检索相似度 TopK 的记忆
- **注入方式**：将召回的记忆，以`system`消息或特殊格式的`user`消息，拼接到短期记忆上下文的最前面。（也可以简单理解为把这段信息加入到提示词Prompt中了）
