**多维数据模型批量校验异常处理机制重构**：针对异常即终止的问题，基于 ThreadLocal 管理请求级校验上下文，实现普通错误持续校验、强依赖错误快速失败及错误统一聚合返回；同时沉淀基于 Worklist + Review 的调用链分析 Skill，辅助复杂调用链与异常节点梳理，提升研发效率。

**AI 提效设计流程优化**：基于 SDD 范式构建 GDE-Design-Loop 插件，通过目标澄清、知识增强与多轮设计质询，实现增量/复杂特性的 AI 辅助设计流程可控化，为 AI Coding 提供高质量 Spec 输入。
**DataFactory 数据编排 Skill 优化**：面向 NL2Pipeline 场景，基于 Bad Case 驱动优化 DataFactory Skill，解决 Few-shot 污染、调度字段丢失及类型反向传播等问题，提升自然语言设计文档到 Platform-native Pipeline DSL 的生成准确性与稳定性，推动平均 Adoption Rate 从 80.12% 提升至 87.3%。

**实习中我遇到最困难的事情，是重构多维数据模型的批量校验异常处理机制。**

当时系统采用异常即终止的处理方式，只要某个校验节点报错，后续校验就不会继续执行。对用户来说，一次只能看到一个错误，需要反复修改、反复提交；对研发来说，校验逻辑分布在比较深的调用链中，而且不同异常对后续流程的影响不同，不能简单地把所有异常都捕获后继续执行。
这个任务最难的地方其实不是写代码，而是**梳理复杂调用链**，并准确判断每类异常的**依赖关系**：哪些只是普通错误，可以记录后继续校验；哪些会导致后续校验失去前提条件，必须快速失败。
为了解决这个问题，我先基于 Worklist 模式维护一个分析清单对函数调用逐层展开；完成一轮分析后，再通过 Review 检查有没有遗漏。基于分析结果，我重新划分了普通错误和强依赖错误，并设计了请求级校验上下文。
具体实现上，我使用 ThreadLocal 管理当前请求的校验上下文，避免在较长的调用链中修改大量方法签名。普通错误会写入上下文并继续执行，强依赖错误则保留快速失败机制；在请求结束时，再统一聚合并返回所有可收集的错误。
最后，系统从“一次返回一个错误”变成了“一次返回一组可修复错误”，同时又没有破坏强依赖场景的正确性。除此之外，我还把调用链分析过程沉淀成了 Worklist + Review Skill，让后续分析类似复杂链路时可以复用。

**DataFactory Skill** **优化**

> 我主要从 **提示词上下文隔离、结构化字段解析、跨层类型传播** 三个方向优化了 DataFactory Skill，解决了生成结果污染、字段丢失和类型覆盖的问题，提升了设计文档到物理模型、数据流和调度流生成结果的准确性。

然后分别展开：
1. **Few-shot 污染治理**  
    原来的 Few-shot 示例里包含 `ps`、`ck_default` 等具体业务值，模型在输入文档只提到 ClickHouse 时，也会错误继承这些示例值。我的优化是将示例中的具体业务值替换为占位符，并增加生成约束：**输入没有明确提供的信息不能从 Few-shot 中补全**，从而避免示例上下文污染真实生成结果。
2. **调度流 retryNum 结构化解析**  
    设计文档明确写了“失败重试 3 次”，但 Agent 最初把它写进了 `description`，而不是结构化的 `retryNum` 字段，导致下游生成器无法识别，最终退化成默认值 0。我从两层修复：**上游约束 Agent 按 Schema 生成 retryNum，下游生成器显式保留和解析 retryNum**，避免关键信息在链路中丢失。
3. **物理模型字段类型逆向覆盖治理**  
    这个问题本质上是不同层级的类型语义被混淆。例如存储层字段可以是 `STRING`，但经过 Inject 转换后，处理层可能已经变成 `INTEGER`。原来的逻辑会用物理模型类型反向覆盖数据流类型。我重新明确了**存储层和处理层的类型边界**，调整类型传播规则，只有当下游类型缺失时才使用物理模型兜底，并同步长度、精度等属性，避免跨层类型污染。
