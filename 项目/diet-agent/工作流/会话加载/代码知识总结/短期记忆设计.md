## 1. 设计定位

本项目的「短期记忆」**不是** AgentScope 框架里的 `Memory`，也**不是**某个独立的 `ShortTermMemory` 类，而是一套由 **Orchestrator 统一管理、MySQL 持久化、按轮按需注入 LLM** 的会话上下文体系。

核心目标：

| 目标            | 实现手段                                           |
| ------------- | ---------------------------------------------- |
| 多轮槽位累积        | `SessionState.slots` 增量合并 + DB 持久化             |
| 识别「换一批」等指代    | `diet_messages` 最近对话摘要 + `lastRecommendations` |
| 澄清/推荐阶段连贯     | `phase` / `currentIntent` 状态机                  |
| 可审计、可 Trace   | 消息原文落库，`agent_trace_id` 关联                     |
| 避免 LLM 隐式记忆漂移 | Agent 每轮 `memory.clear()`，上下文显式拼进 prompt       |

一句话概括：**权威状态在 DB + Orchestrator，LLM 只读本轮拼好的结构化快照。**

## 2. 记忆分层架构
```
┌─────────────────────────────────────────────────────────────────┐
│                     短期记忆（会话级，MySQL）                      │
├──────────────────────────┬──────────────────────────────────────┤
│  结构化状态层             │  对话转录层                           │
│  diet_sessions           │  diet_messages                       │
│  ─ SessionState          │  ─ user / assistant 原文             │
│    · slots (7 维槽位)     │  ─ intent / traceId                  │
│    · phase               │  ─ 按需切片 → ConversationTurn        │
│    · currentIntent       │    （120 字摘要，供 IntentAgent）       │
│    · lastRecommendations │                                      │
│    · sourceMode (_meta)  │                                      │
└────────────┬─────────────┴──────────────────┬───────────────────┘
             │                                │
             ▼                                ▼
      SessionStateService              SessionService
      （loadOrCreate / save）          （appendMessage /
                                        recentConversationTurns）
             │                                │
             └────────────┬───────────────────┘
                          ▼
               DietOrchestratorService
               （唯一写入方 + 上下文组装）
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    IntentAgent      ClarifyAgent   RecommendResponseAgent
    （recentHistory   （mergedSlots   （mergedSlots +
     + knownSlots）    + userInput）   top3 候选）
```

### 2.1 结构化状态层（SessionState）
对应 `diet_sessions` 表，由 `SessionStateService` 读写，`DietOrchestratorService` **独占写入**。
```java
SessionState {
    sessionId, userId,
    phase,              // START | CLARIFY | RECOMMEND | PLAN
    sourceMode,         // PERSONAL | PUBLIC
    currentIntent,
    slots,              // SlotBundle 7 维累积槽位
    lastRecommendations // 已推荐 mealId 列表（累积去重）
}
```

**记忆语义**：
- `slots`：跨轮**累积**的用户偏好（餐次、场景、口味等），本轮 IntentAgent 只输出增量，由 `SlotMergeService` 与历史合并
- `lastRecommendations`：本会话已展示过的餐食 ID，供「换一批」排除重复
- `phase` / `currentIntent`：告诉 Orchestrator 当前会话卡在哪个阶段，辅助路由与规则矫正
- `sourceMode`：持久化在 `slots._meta`，保证多轮始终在同一数据源（PERSONAL / PUBLIC）内检索

### 2.2 对话转录层（ConversationTurn）

对应 `diet_messages` 表，由 `SessionService` 追加与查询。
每轮对话结束时写入两条（或一条）消息：

| 时机      | role      | intent    | 说明               |
| ------- | --------- | --------- | ---------------- |
| 收到用户输入后 | user      | null      | 用户原文             |
| 返回助手回复后 | assistant | 最终 intent | 追问 / 推荐文案 / 固定引导 |

读取时通过 `recentConversationTurns(sessionId, userId, n)` 转为 `ConversationTurn`：
```java
ConversationTurn {
    role,       // user | assistant
    intent,     // assistant 轮次携带，user 轮次可为 null
    summary,    // content 截断至 120 字符（省 token）
    timestamp
}
```

**记忆语义**：
- 完整原文永久留在 `diet_messages`（审计、评估、Trace 交叉定位）
- 注入 LLM 时只取最近 **n 条**（Orchestrator 固定传 `n=3`），且每条最多 **120 字**
- **目前仅 IntentAgent 消费** `recentHistory`；ClarifyAgent / RecommendResponseAgent 不读对话历史，依赖合并后的 `slots`

### 2.3 瞬态 Prompt 上下文

每轮 Agent 调用前，Orchestrator 或各 `AgentService` 将上述两层记忆**显式序列化**进 user prompt，而非依赖 Agent 内部记忆自动累积。

| Agent                  | 注入的短期记忆字段                                            |
| ---------------------- | ---------------------------------------------------- |
| IntentAgent            | `recentHistory` + `knownSlots` + `slotOptions` + 当前句 |
| ClarifyAgent           | `mergedSlots` + `missingSlots` + 用户原话                |
| RecommendResponseAgent | `mergedSlots` + `sourceMode` + top3 候选 + 用户原话        |

## 3. 一轮对话中的读写时序

以「工作很忙推荐快速的 → 午餐 → 换一批」为例：

```
轮次 1  用户：「工作很忙，推荐快速的」
  ① appendMessage(user)
  ② recentConversationTurns(3) → []          // 尚无历史
  ③ IntentAgent(knownSlots=空, recentHistory=[])
  ④ merge slots → scene=工作, convenience=快速
  ⑤ save SessionState + appendMessage(assistant, 推荐结果)
  ⑥ lastRecommendations += [id1, id2, id3]

轮次 2  用户：「午餐」
  ① appendMessage(user)                       // 此时 recent 含轮次 1 的 user+assistant
  ② recentConversationTurns(3) → 2 条摘要
  ③ IntentAgent(knownSlots=上轮 slots, recentHistory=2条)
  ④ merge → mealTime=午餐，保留 scene/convenience
  ⑤ ...

轮次 3  用户：「换一批」
  ① appendMessage(user)
  ② recentConversationTurns(3) → 最近 3 条（含 assistant 推荐 intent）
  ③ IntentAgent 结合 recentHistory 识别 MEAL_ADJUST
  ④ IntentRevise 校验 lastRecommendations 非空
  ⑤ handleAdjust → excludeMealIds = lastRecommendations
  ⑥ 新推荐写入 lastRecommendations（累积追加）
```

**关键时序细节**：用户消息在 IntentAgent 调用**之前**落库，因此 recentConversationTurns 读到的是**不含当前**句的历史；当前句通过 prompt 的「当前这一句」字段单独传入。这样避免重复，也保证 IntentAgent 对「当前输入」与「历史上下文」分工明确。

## 4. 各记忆字段的消费方

| 记忆字段                       | 写入方                          | 读取方                                                             | 用途                  |
| -------------------------- | ---------------------------- | --------------------------------------------------------------- | ------------------- |
| `slots`                    | Orchestrator（merge 后 save）   | IntentAgent（knownSlots）、ClarifyAgent、RecommendResponseAgent、检索层 | 多轮偏好累积              |
| `lastRecommendations`      | Orchestrator（推荐成功后 append）   | IntentReviseService、handleAdjust → MealRankService              | 「换一批」去重             |
| `phase`                    | Orchestrator                 | 排查、评估；间接影响澄清/推荐分支                                               | 会话阶段                |
| `currentIntent`            | Orchestrator                 | 落库 assistant 消息的 intent 字段                                      | 历史 intent 标注        |
| `sourceMode`               | 首屏绑定后持久化                     | 检索数据源隔离                                                         | PERSONAL/PUBLIC 不混查 |
| `diet_messages` 原文         | SessionService.appendMessage | recentConversationTurns → IntentAgent                           | 指代、调整类意图            |
| `ConversationTurn.summary` | SessionService.summarize()   | IntentAgent prompt                                              | 压缩 token 的对话摘要      |

**不读短期记忆的组件**：ClarifyRuleService、MealSearchService、MealRankService、RiskGuard 等 Java 规则/检索层只消费 SlotBundle 和业务 ID，不直接访问消息表。

## 5. 配置与边界
### 5.1 配置项
```yaml
# application.yml
diet:
  session:
    max-history-turns: 10   # recentConversationTurns 上限（Orchestrator 实际请求 n=3）
```
- Orchestrator 硬编码 `recentConversationTurns(..., 3)`，与 IntentAgent prompt 规则（「最近 3 轮 assistant 已推荐」）对齐
- `max-history-turns` 是 `SessionService` 的安全上限：`limit = min(n, maxHistoryTurns)`

### 5.2 摘要与容量边界

| 边界                  | 值        | 原因                           |
| ------------------- | -------- | ---------------------------- |
| 注入 LLM 的对话条数        | 3 条消息    | 覆盖「上一轮推荐 + 当前调整」足够；控制 token  |
| 单条摘要长度              | 120 字符   | 推荐卡片 JSON 较长，截断后仍保留关键语义      |
| lastRecommendations | 会话内累积    | 多轮「换一批」持续排除；无 TTL，随会话结束      |
| 会话状态 TTL            | 无（DB 持久） | 前端持 sessionId 即可恢复；无 Redis 层 |
### 5.3 并发与一致性

同 `sessionId` 请求经 `sessionLocks` 串行化，保证：
- 两轮同时 merge slots 不会互相覆盖
- `lastRecommendations` 追加不会丢 ID
- `recentConversationTurns` 与 `appendMessage` 顺序一致

## 6. 与 Agent Memory（InMemoryMemory）的对比
本项目每个 ReActAgent 构建时仍挂载 AgentScope 的 `InMemoryMemory()`，但**业务多轮记忆完全不依赖它**。

### 6.1 对照表

| 维度             | 系统短期记忆                                   | Agent Memory（InMemoryMemory）            |
| -------------- | ---------------------------------------- | --------------------------------------- |
| **存储位置**       | MySQL（`diet_sessions` + `diet_messages`） | JVM 堆内，Agent 实例私有                       |
| **生命周期**       | 随 sessionId 持久，跨请求/重启可恢复                 | 随 Agent 实例；Factory LRU 淘汰后丢失            |
| **写入方**        | Orchestrator / SessionService（Java 显式）   | AgentScope 框架在 `agent.call()` 内自动追加 Msg |
| **读取方式**       | 各 Service 拼进 user prompt 结构化字段           | 框架自动注入下一轮 LLM 上下文                       |
| **数据结构**       | 结构化：SlotBundle、Intent、mealId 列表、摘要       | 非结构化：Msg 列表（原始对话）                       |
| **多 Agent 共享** | 是，同一 SessionState 供所有 Worker 只读          | 否，每个 Agent 独立 Memory                    |
| **Trace 可见性**  | 完整：DB 原文 + Trace 事件                      | 仅当轮 call 内部；clear 后不保留                  |
| **每轮策略**       | load → 业务 → save；按需切片注入                  | `memory.clear()` **清空**，不累积             |
| **设计意图**       | 权威业务状态，可审计、可评估                           | 满足 AgentScope API 要求的占位容器               |

### 6.2 为何不用 Agent Memory 做多轮

1. **单一权威源**：`SessionState` 已是 ground truth；若 Agent Memory 也累积，会出现双写不一致（槽位被 LLM 改写、推荐 ID 无法结构化存储）。
2. **结构化优先**：槽位、排除列表、phase 必须 Java 可校验；Msg 列表无法直接驱动检索与规则。
3. **可观测**：Orchestrator 拼 prompt 的内容完整进入 `AGENT_CALL` Trace；隐式 Memory 难以对齐业务字段。
4. **会话隔离**：`AgentFactory` 按 sessionId 缓存 AgentSet 是为避免**不同用户**串话；同会话内仍每轮 clear，不靠 Memory 续聊。
5. **AgentScope 轻量用法**：本项目把 ReActAgent 当「LLM 网关 + JSON 生成器。
