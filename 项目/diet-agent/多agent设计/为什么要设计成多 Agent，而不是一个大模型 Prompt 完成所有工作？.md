这个推荐场景包含多个职责不同的阶段。
意图识别需要判断用户想做什么，**槽位澄清**需要确定信息是否充分，**检索重排**负责筛选候选，**推荐生成**负责把结果组织成用户能理解的建议。
如果把这些都放进一次模型调用，模型可能在信息不足时直接推荐；结果出错后，也比较难区分是**需求理解错了**，还是**候选筛选**或**生成**出了问题。

所以我采用**编排中枢**加**专职 Worker** 的结构，让各推理单元输出结构化结果，由后端统一决定下一步。比如缺少必要信息时进入澄清，满足条件后才进入检索和推荐。==模型负责理解与生成，流程控制由确定性的代码完成。==

这个拆分也服务于 Trace 和评估：每个节点都可以记录输入输出、单独定义质量指标，低分样本能够定位到具体环节，后续可以只调整某个节点。

代价是模型调用可能增多，耗时、Token 和维护成本都会增加。==因此，模型负责理解与生成，流程控制由确定性的代码完成。==
