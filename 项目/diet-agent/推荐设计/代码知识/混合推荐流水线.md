## 1. 为什么要分层

饮食推荐如果完全交给 LLM，常见问题是：
- **餐食幻觉**：模型编造不存在的菜名或 ID
- **成本不可控**：每轮都把全库菜单塞进 Prompt
- **结果不可解释**：无法说明「为什么召回这几道菜」
- **排序不稳定**：同一输入多次调用结果波动大

本项目在 `DietOrchestratorService#completeRecommendation` 中把推荐拆成 **检索 → 重排 → 生成** 三层，LLM 只负责最后一层的「解释与包装」。

## 2. 三层流水线架构
```
用户槽位 slots
      │
      ▼
┌─────────────────────────────────────┐
│ 第一层：MealSearchService（宽召回）   │
│ MySQL JSON_OVERLAPS，最多 50 条      │
│ LLM 不参与                           │
└─────────────────────────────────────┘
      │ candidates (≤50)
      ▼
┌─────────────────────────────────────┐
│ 第二层：MealRankService（精排）       │
│ 7 维 overlap 比例打分，Top10         │
│ 过滤 excludeMealIds（换一批）         │
│ LLM 不参与                           │
└─────────────────────────────────────┘
      │ ranked (≤10)
      ▼
┌─────────────────────────────────────┐
│ 第三层：RecommendResponseAgentService │
│ MMR多样性重排取 Top3 → LLM 生成 reason + speechText│
│ mealId 必须在候选白名单内             │
└─────────────────────────────────────┘
      │
      ▼
RiskGuardService（合规）→ ChatResponse
```

## 3. 各层职责与边界
### 3.1 第一层：MealSearchService

**职责**：按 `sourceMode + userId + slots` 从 DB 召回「至少有一个标签维度有交集」的候选。
- 调用 `MealService.search()` → `MealMapper.search`
- 上限 `SEARCH_LIMIT = 50`
- **设计取向：宁可多召回，不在 DB 层做精细排序**

Trace 事件：`MEAL_SEARCHED`（candidateCount + candidates）
### 3.2 第二层：MealRankService

**职责**：在候选集内按「用户需求满足度」二次打分排序。
核心算法（`slotScore`）：
- 7 个槽位维度各自计算 `overlap = 命中标签数 / 用户该维标签数`
- 7 维求平均 → `matchScore ∈ [0, 1]`
- 按 matchScore 降序，取 Top10
- 过滤 `excludeMealIds`（MEAL_ADJUST 换一批场景）

**与 Search 的区别**（代码注释原文）：search 只要槽位有交集就返回；rank 是比较用户槽位是否更大程度得到满足。
举例：用户 healthGoal = \[清淡, 高蛋白\]
- 鸡胸肉（healthGoal 是清淡 高蛋白 则命中 2/2）→ score = 1.0
- 猪肘（healthGoal 是高蛋白 则命中 1/2）→ score = 0.5

Trace 事件：`MEAL_RANKED`
### 3.3 第三层：RecommendResponseAgentService

**职责**：一次 LLM 调用同时产出：
- `recommendations[]`：每项 `{ mealId, reason }`
- `speechText`：面向用户的口语回复

**防幻觉约束**：
1. Prompt 明确要求「不要编造候选之外的餐食」
2. `parseOptions()` 只采纳 `topMeals` 白名单内的 mealId
3. reason 为空的不采纳；缺失 reason 用 `templateReason()` 兜底
4. LLM 失败时用 `templateOptions()` + `templateSpeech()` 全模板兜底

Trace 事件：`RECOMMEND_RESULT_BUILT` → `RESPONSE_AGENT_RESULT`

## 4. 空结果与异常路径

| 场景        | 处理                                  |
| --------- | ----------------------------------- |
| ranked 为空 | 按 sourceMode 返回不同空库提示，不走 LLM        |
| Top3 为空   | 直接返回「暂时没有找到很匹配的餐食」                  |
| LLM 异常    | 模板理由 + 模板 speechText，仍返回 Top3 卡片    |
| Guard 拦截  | 替换 speechText 为 conservativeMessage |
