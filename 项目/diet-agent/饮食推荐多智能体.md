技术栈：Agentic Workflow、Trace Engineering、Eval Engineering、MySQL、SpringBoot、AgentScope(hook)

项目简介：面向日常就餐决策难题场景，打造一款结合用户实时心情、场景、健康诉求等多维动态信息的智能饮食推荐 Agent。通过编排多 Agent 协作，实现意图识别 → 槽位澄清 → 标签检索重排 → LLM 推荐 的完整对话式推荐链路，并设计 Trace 全链路监控与离线评估体系。

核心设计：
+ **评估体系设计与评估闭环**：通过批量解析 Trace 的离线评估的方式，使用 后端规则、LLM Judge、用户反馈 三者加权评估输出百分制评分报告，覆盖意图识别准确率、Token消耗、端到端耗时等10+指标，低分样本回流反哺优化系统设计，形成 Trace 标注—批量评估—指标驱动迭代优化的完整闭环；
+ **全链路可观测能力设计**：针对 LLM 黑盒的不确定性，在业务关键节点采集输入与输出等核心指标的 Trace 事件，落库可回溯，支撑线上排查逐步回放，为每一次用户对话提供全链路可观测能力支撑；
+ **后端多 Agent 协作架构**：采用编排中枢+专职Worker分层模式，将意图理解、槽位澄清、推荐生成、质量评估解耦为独立推理Agent单元；LLM 仅负责结构化推理输出，会话流转与状态跃迁由编排层统一管控；
+ **意图识别与规则兜底**：意图识别 Agent 识别 6 类意图与 7 维槽位，叠加 意图状态矫正、低置信降级、关键词 Fallback 三层兜底，避免错误路由与低质量推荐；槽位抽取通过词典强约束，避免幻觉；

**测试结果**：  
基于100条已标注模拟请求完成批量评估，规则分 = 87.06，LLM Judge = 76.90，请求成功率100%，意图准确率99%，槽位准确率95.83%，澄清准确率、多轮一致性、安全合规率和幻觉控制率均为100%，Fallback率为0%。

**6 类意图**：推荐餐食、规划餐次、澄清、调整上一轮、健康预警、其他
**7 维槽位**：餐次、**菜系、口味、心情、场景、健康诉求、便携性**

**意图状态矫正**：结构化槽位矫正、会话状态矫正、依赖置信度矫正、关键词矫正
**关键词 Fallback**：LLM调用或解析失败，用关键词重新生成一个基础意图
**低置信度降级**：需要澄清


**项目优化实例**
+ intent agent中mealplan过于强调三餐和一日计划，导致用户问帮我安排午餐晚餐，清淡点，识别为meal_recommendation。在提示词层面强调两个及以上的参词规划；在java规则层判断，mealtime槽位是否大于1。
+ 帮我选一顿饭， 这个问题从语义上来看是确实是在请求推荐的，但是确实必要的推荐条件，最后模型把它识别了饮食推荐。 所以加上必要槽位存在性(健康目标，菜系，口味，场景，方便性)的判断
+ 错误推荐，用户快速连续点了两次“换一批”，第二次却又看到了第一次的菜。换一批是追加。
+ 重复度高，午饭来一份营养均衡的。最终推荐：上海葱油拌面、重庆小面、云南鸡汤米线。都是粉面，相似度太高了。使用MMR进行多样性重排，基于jaccard相似度定义多样性得分。


**遇到的困难，你是如何解决的？**
最开始如果过度依赖 Agent 自身记忆和模型判断，会出现三个问题：**多轮上下文不稳定**、**同一句话可能路由到不同分支**、**模型调用失败时整条请求容易中断**。

我的解决方案是把系统设计成“**LLM负责理解和表达**，**Java状态机负责决策和约束**”。

+ 通过编排中枢固定主流程形成agentic flow：意图识别 → 规则矫正 → 意图路由。（推荐澄清、规划、换一批、健康预警、其他）
+ **会话状态**由编排中枢显式传入，其中包括历史槽位，历史推荐ID，会话阶段
+ 所有 LLM 调用增加了降级方案( 意图识别失败时走关键词兜底，澄清失败时使用模板追问，推荐生成失败时使用模板理由和模板回复。)
